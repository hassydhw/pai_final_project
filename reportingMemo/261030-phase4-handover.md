### 3.2 ブロックの初期配置の見直し（10/29）
- アームの先端（把持中心）が床すれすれで届くのは土台から r ≈ 0.217m。ただし指とブロックの幅の分だけ余裕があり、**掴める限界は実測で r ≈ 0.24m**（0.245m で失敗）。

### 3.3 VR 空間にアームとブロックを表示（10/29、`feature/vr-scene`）
- それまで VR 内は青いグリッドと赤い球だけで、操作者は PC の MuJoCo 画面を見て操作していた。
- サーバーが接続時に MJCF から各パーツの形・大きさ・色を送り、その後は位置・姿勢を送る。Quest 側の Three.js が同じ形を描く（MJCF を変えても HTML の修正は不要）。
- **アームを 2 倍（= 1 / SCALE）に拡大し、コントローラの位置にグリッパーが重なるように配置**（「自分の手がグリッパーになる」感覚）。
- 影の描画を追加 → ユーザー評価「影のおかげで操作性がかなり良くなった」。
- `HOME_TARGET` を (0.15, 0, 0.15) → (0.15, 0, 0.12) に変更（元の位置はわずかに届かず、VR で接続直後にグリッパーが手から 5cm ずれて見えた）。
- 遅れとカクつきの調査（§5.2）：遅れの大半は LocalTunnel の往復。送信を 30Hz → 60Hz・一定間隔に変更。
- **LAN 直結（自己署名 HTTPS）を試したが、Quest から接続できず断念**（Phase 2 でも同様だった）。トンネル方式のままとし、LAN 直結のコードは削除。
- `start_teleop.sh`：前回のトンネル（Ctrl+Z で一時停止したまま残ったものなど）を起動時に自動で終了させる処理を追加（サブドメインが「使用中」で別の URL になる問題への対処）。

### 3.4 データレコーダー（10/29〜30、`feature/recorder`）
- `teleop_server.py --record`（`./start_teleop.sh --record`）で記録。ブロックが置かれ Quest 3 が接続していれば自動で開始し、**配置成功の 1 秒後に保存**（離して手を引く動きまで含める）。成功前の B ボタン・届かない場所に出た・切断・120 秒超過は破棄。
- **画像はテレオペ中に描かず、記録した全状態（`sim/qpos`）から `render_episodes.py` で後から描く。** 理由：物理ループを重くしない、viewer と GL がぶつからない、解像度やカメラを後から変えられる。描画には記録時の MJCF（全文を添付）を使う。
- カメラ 2 台を MJCF に追加：`cam_front`（アームの真後ろやや上から俯角 40°、fovy 45）、`cam_wrist`（掌の後ろから指先を見下ろす、fovy 70）。320×240。
- **目標の球（手の位置 = 行動そのもの）は記録画像に写さない**（geom group 2 に移動）。viewer と VR では従来どおり見える。
- `test_recorder.py`：Quest 3 の代わりに手の位置を送って Pick & Place し、保存・破棄・画像追加まで確認する結合テスト。

### 3.5 VR 内の机の高さを目の高さ基準に（10/30）
- 起動時に手を下げていると机が低く出る問題 → Unity の Eye Level のように、**VR 開始時の HMD の高さにアームの最上部（ホーム姿勢で z = 0.23m、VR では 0.46m 下）が来るよう机の高さを固定**。
- 高さは「机からの手の高さ」で絶対的に決まる（手を机より下げるとグリッパーは机の上で止まる）。前後左右は従来どおり相対。A ボタンは前後左右の原点だけを取り直す。
- ユーザー確認：起動時の高さは問題なし。

### 3.6 学習パイプラインの試行（10/30、`feature/training`）
- 学習用に別の venv `~/lerobot_env` を作成（LeRobot 0.6.1、torch 2.11 + CUDA 13、mujoco、h5py。約 5.6GB）。LeRobot が `numpy<2.3` を要求し、テレオペ用の `~/pai_env`（numpy 2.5）と共存できないため。
- `convert_to_lerobot.py`：HDF5 → LeRobot 形式。画像は動画ではなく PNG で保存（FFmpeg が入っていないため。小さなデータセットなら十分）。
- ACT を 4 エピソードで試験学習し、`eval_policy.py` で MuJoCo 上で評価（§5.4）。**データ形式はこのまま学習に使えると判断。**
- 試験で見つかった問題 → 「配置成功の瞬間に記録が終わるので、離す動作のデータが少ない」→ 成功後も 1 秒記録するよう修正（§3.4）。
- 試験に使った 4 エピソードは、成功後 1 秒を含まない旧形式。ユーザーが `old_data/` に退避済み。

## 4. 設計上の判断（Phase 4 で追加したもの。変えるときは理由を踏まえること）

1. **VR 表示はサーバーが送る位置・姿勢をそのまま描く**（クライアント側で物理計算しない）。MJCF の geom を自動で送るので、モデルを変えても HTML は変更不要。
2. **座標の変換は `robot_to_xr` / `xr_to_robot` の 1 か所に集約**。手の入力と VR 表示が必ず一致する。
3. **高さは絶対、前後左右は相対。** 机の高さは VR 開始時の目の高さで固定（`ARM_TOP_Z = 0.23`、`EYE_TO_ARM_TOP = 0.0`）。クライアントが `eye` を送らないとき（テストなど）は従来どおり手の位置に合わせる。
4. **状態は 60Hz の一定間隔で送る。** 物理ループは毎回最新の状態を渡し、送信側が一定周期で送る（周期を揃えないとカクつく）。
5. **記録は状態のみ、画像は後から描く**（§3.4 の理由）。`sim/qpos` から画像は一意に決まる。
6. **行動（action）は `data.ctrl`（関節の目標角 4 + 指の目標開き量 2）。** 手の目標位置（`action_ee`）も保存してあるので、エンドエフェクタ空間の方策も試せる。
7. **目標の球を記録画像に写さない。** 写すと答え（行動）を画像で見せることになる。
8. **学習の venv はテレオペと分ける**（numpy の版の衝突）。
9. **LeRobot の画像は PNG**（FFmpeg 不要）。データが大きくなって読み込みが遅ければ、FFmpeg を入れて動画（`use_videos=True`）にすることを検討。

## 5. 計測値・実験結果（レポート用）

### 5.1 アームの到達範囲
| 項目 | 値 |
|---|---|
| 先端が床すれすれ（z = 0.018m）で届く水平距離 | r ≈ 0.217m |
| 実際に掴める限界（指とブロックの幅の分だけ広い） | r ≈ 0.24m（0.245m で失敗） |
| ブロック配置範囲の最も遠い角（変更前 → 変更後） | 0.239m → 0.211m |

### 5.2 テレオペの遅れ（10/29 計測）
| 要因 | 遅れ |
|---|---|
| LocalTunnel（loca.lt までの往復 0.20〜0.23 秒を、行きと帰りで 2 回通る） | 約 0.4 秒 |
| アームの物理的な追従（位置制御） | 半分まで 40ms、9 割まで 110ms |
| 状態の送信（30Hz → 60Hz に変更） | 届く間隔 16.7ms、ばらつき 0.7ms（ローカル計測） |

- 送るデータ量：シーン 1.8KB（接続時 1 回）、状態 600B/回（60Hz で約 35KB/s）。
- ユーザー評価：遅れとカクつきは「許容範囲」。影で操作性は大きく改善。

### 5.3 学習時間：CPU と GPU（ACT、100 ステップ、バッチ 8、4 エピソード）
| | GPU（RTX 3080 Ti Laptop 16GB） | CPU（24 スレッド） |
|---|---|---|
| 100 ステップ | 45 秒 | 4 分 50 秒（約 6.4 倍） |
| 1 ステップの計算時間 | 約 0.15 秒 | 約 2.6 秒（約 17 倍） |
| 1 万ステップの見積もり | 約 1 時間 | 約 7.5 時間 |

- GPU では画像の読み込みが追いつかず待ちが出るため、全体の差は計算の差より小さい。
- ACT のパラメータ数は 52M。チェックポイント 1 個 591MB。

### 5.4 試験学習の結果（4 エピソード・2,048 フレーム、ACT、4,000 ステップで評価）
- 損失：26.0（20 ステップ）→ 4.5（100）→ 0.60（3,000）→ 0.30（5,000）。
- `eval_policy.py` で 10 回試行：**配置成功 0/10、掴んで持ち上げ 5/10、つかみ損ね 5/10。**
- 失敗の仕方：(a) 緑のエリアの上まで運ぶが降ろして離さない、(b) つかみ損ねてもそのままエリアへ向かう。どちらも示範が少ないときの典型。(a) は記録が成功の瞬間で終わっていたことも一因 → 修正済み。
- 評価は 1 試行あたり約 60 秒（描画 + 推論）。

```bash

cd ~/pai_final_project

  --policy.type=act --policy.device=cuda --policy.push_to_hub=false --output_dir=outputs/train/<名前> \
  --steps=<N> --batch_size=8 --save_freq=5000 --wandb.enable=false --num_workers=12
~/lerobot_env/bin/python eval_policy.py outputs/train/<名前>/checkpoints/<ステップ>/pretrained_model --episodes 10

# --- テスト（~/pai_env）---
```

## 8. 次にやること（Phase 5：データ収集と本番の学習）

1. **準備（記録の前にやっておく。WSL の再起動を伴うため）**
   - `C:\Users\<ユーザー名>\.wslconfig` の `[wsl2]` に `memory=20GB` を追記 → PowerShell で `wsl --shutdown`。
   - 学習前のチェックリスト：Chrome など重いアプリを閉じる／AC 電源・電源モード「最適なパフォーマンス」／スリープと蓋を閉じたときの動作を無効／Windows Update の再起動を一時停止／冷却（吸排気口をふさがない）／学習中はテレオペや GPU を使うアプリを動かさない／ターミナルを閉じない（`tmux` 推奨）。
2. **データ収集：`./start_teleop.sh --record` で約 50 エピソード**
   - 目安：1 エピソード 15〜20 秒 + 再配置 2 秒 → 50 本で 20〜30 分。まず 20〜30 本で一度学習し、足りなければ追加するのでもよい。
   - コツ：毎回同じ手順で（上から近づく → 降ろす → 掴む → 持ち上げる → エリアの上へ → 降ろす → 離す → **手を上に引く**）。`SUCCESS!` のあと 1 秒は記録が続くので、手を引く動きまで行う。
   - つかみ損ねたら、やり直すより B ボタンで破棄したほうがデータがきれいになる。
3. **画像の追加と変換**：`render_episodes.py --preview` → プレビューを数本確認 → `convert_to_lerobot.py --overwrite`。
4. **本番の学習**（Claude は手順 1 のチェックリストを必ずリマインドする）
   - まず 2 万ステップ（GPU で約 2 時間）、`--save_freq=5000`。
   - 実行は `tmux` の中で（例：`tmux new -s train` → 学習コマンド → `Ctrl+B` `D` で切り離し、`tmux attach -t train` で戻る）。
5. **評価**：各チェックポイントを `eval_policy.py --episodes 10` で評価（1 チェックポイント約 10 分）。成功率と GIF で比較する。
6. **成功率が低いときの改善候補**（効きそうな順）：データを増やす／学習ステップを増やす／ACT の時間的アンサンブル（`--policy.temporal_ensemble_coeff=0.01 --policy.n_action_steps=1`）で動きを滑らかに／`action_ee`（手先の目標位置）を行動にした方策との比較。
7. **まとめ**：構築ガイドに Phase 3〜5 の章を追記、デモ動画（テレオペの様子 + 学習した方策の動き）、レポート。
8. **git の整理**：`feature/training` を `main` にマージ。`old_data/` は一部（プレビュー画像・メタ情報の 8 ファイル、448KB）が `05b11d7` でコミットされている。データを git に入れない方針なら、`.gitignore` に `old_data/` を追加して `git rm -r --cached old_data` で管理対象から外す。

## 10. 既知の制約・課題
- LocalTunnel 経由のため、操作の遅れが約 0.4 秒ある（LAN 直結は Quest から接続できず断念）。
- 評価が遅い（1 試行約 60 秒）。たくさん評価するときは試行数を絞るか、待ち時間を見込む。
- 学習時はデータの読み込みが律速（GPU 使用率 27%）。データが増えて遅くなれば、動画形式への切り替え（FFmpeg が必要）を検討。
- SO-101 の簡易モデル（手首のロール軸なし、リンク長は実機と異なる）。手の回転は使っていない。
- `eval_policy.py` は成功した時点で試行を打ち切るので、成功後に手を引く動きまでは評価していない。
